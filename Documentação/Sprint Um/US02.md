
## US02 - Lançamento de Horas e Classificação de Atividades

**User Story:** "Como Desenvolvedor, quero lançar minhas horas trabalhadas informando o projeto, a task, o período (início e fim) e o tipo de atividade realizada (Feature, Correção de Bug, Reunião ou Documentação), para que a empresa tenha rastreabilidade sobre como o tempo está sendo distribuído entre inovação e correção de falhas, e gestores possam aprovar ou rejeitar lançamentos retroativos com justificativa."

<details>
<summary>Critérios de Aceitação</summary>

- Ao lançar "Correção de Bug", o sistema deve solicitar obrigatoriamente o vínculo com a tarefa original para rastrear a origem da falha.
- Lançamentos retroativos (dias anteriores ao atual) exigem uma justificativa por escrito e aprovação manual do Gerente.
- O desenvolvedor deve selecionar o "Tipo de Atividade" (Feature, Correção de Bug, Reunião, Documentação) em cada lançamento.
- O sistema não deve permitir lançamentos que excedam 24 horas em um único dia civil.
- Cada lançamento deve estar vinculado a um Projeto e a uma Task previamente aprovada.

</details>

<details>
<summary>Cenários</summary>

**Cenário 1: Lançamento de Feature (Fluxo Padrão)**
- Dado que o desenvolvedor finalizou uma task de "Feature";
- Quando ele seleciona o tipo "Feature", insere 4 horas e clica em "Lançar";
- Então o sistema registra as horas e atualiza o custo acumulado do projeto imediatamente.

**Cenário 2: Rastreabilidade de Bug**
- Dado que o desenvolvedor está lançando horas de "Correção de Bug";
- Quando ele tenta salvar sem selecionar a "Task Original" que gerou a falha;
- Então o sistema bloqueia o lançamento e exibe: "Para correções, é obrigatório vincular a tarefa de origem para análise de causa raiz".

**Cenário 3: Lançamento Retroativo com Justificativa**
- Dado que o desenvolvedor esqueceu de lançar as horas de ontem;
- Quando ele tenta realizar o lançamento com a data de ontem;
- Então o sistema abre um campo obrigatório de "Justificativa" e altera o status do lançamento para "Aguardando Aprovação do Gerente".

**Cenário 4: Bloqueio de Lançamento em Task não Aprovada**
- Dado que uma task ainda está com status "Pendente de Aprovação";
- Quando o desenvolvedor tenta lançar horas nela;
- Então o sistema impede a ação e informa: "Não é permitido lançar horas em tarefas que ainda não foram validadas pelo Líder Técnico".

</details>

<details>
<summary>Regras de Negócio</summary>

**Fluxo de estado:**
- Lançamento com data de hoje → PENDENTE
- Lançamento com data anterior → AGUARDANDO_APROVACAO + justificativa obrigatória
- Gerente aprova → APROVADO
- Gerente rejeita → REJEITADO + motivo_rejeicao obrigatório

**Regras de validação:**
- Todo lançamento deve estar vinculado a uma task com status aprovado.
- Se tipo_atividade == CORRECAO_BUG, id_tarefa da task de origem é obrigatório.
- Soma de horas do mesmo usuário no mesmo dia não pode ultrapassar 24h.
- Se data_lancamento < hoje, justificativa é obrigatória.

**Atores:**
- Desenvolvedor — CRUD na página de Entrada/Saída.
- Gerente — aprova ou rejeita lançamentos com status AGUARDANDO_APROVACAO.

</details>

<summary>Dicionário de Dados</summary>

## Dicionário de Dados — US04

### Apontamento de Horas

| Nome da variável | Descrição | Tipo de dado | Tamanho | Restrição |
| :--- | :--- | :--- | :--- | :--- |
| id | Identificador único do apontamento | Integer | - | PK, Not Null |
| usuarioId | Usuário que realizou o apontamento | Integer | - | FK, Not Null |
| tarefaId | Tarefa vinculada ao apontamento | Integer | - | FK, Nullable |
| tituloSessao | Título do apontamento | String | 255 | Not Null |
| descricao | Descrição detalhada da atividade | String | 1000 | Nullable |
| tipoAtividade | Tipo da atividade realizada | Enum | - | ANALISE, DESENVOLVIMENTO, TESTES, CORRECAO_BUG, FEATURE |
| dataLancamento | Data do apontamento | Date | - | Not Null |
| inicio | Hora de início da atividade | Time | - | Not Null |
| fim | Hora de fim da atividade | Time | - | Not Null |
| justificativa | Justificativa para lançamento retroativo | String | 1000 | Not Null quando dataLancamento < data atual |
| motivoRejeicao | Motivo informado pelo Gestor ao rejeitar | String | 500 | Not Null quando estado = REJEITADO |
| estado | Estado atual do apontamento | Enum | - | PENDENTE, AGUARDANDO_APROVACAO, APROVADO, REJEITADO |
| dataCriacao | Data de criação do registro | Timestamp | - | Not Null |

</details>

<details>
<summary>DoR — Definition of Ready</summary>

| Critério | Descrição |
| :--- | :--- |
| **Tipos de atividade definidos** | Análise, Desenvolvimento, Testes, Correção de Bug e Feature confirmados para seleção no apontamento. |
| **Fluxo de status definido** | Definido que lançamento criado vai para aprovação, podendo ser aprovado ou rejeitado com motivo obrigatório. |
| **Regra de lançamento retroativo definida** | Definido que lançamento com data anterior ao dia atual exige justificativa obrigatória e entra automaticamente na fila de aprovação. |
| **Campos do apontamento definidos** | Projeto, título da sessão, descrição, responsável, tipo de atividade, horário de início, horário de fim, data de lançamento e justificativa quando retroativo. |

</details>

<details>
<summary>DoD — Definition of Done</summary>

| Critério | Descrição |
| :--- | :--- |
| **Cálculo de horas correto** | Total por registro calculado corretamente a partir do horário de início e fim. Total da semana recalcula conforme filtros aplicados. |
| **Regra retroativa aplicada** | Lançamento com data anterior ao dia atual não é enviado sem justificativa preenchida. |
| **Fluxo de status verificado** | Lançamento enviado aparece em Aguardando Aprovação. Aprovado aparece em Aprovados. Rejeitado aparece em Rejeitados com motivo visível. |
| **Filtros corretos em todas as abas** | Filtro por projeto e por data funcionam corretamente em todas as páginas, com totais recalculados após aplicação. |

</details>
